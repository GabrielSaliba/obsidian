1. <span style="color:rgb(255, 192, 0)">The normative architecture does not define product archival.  </span>
   The Linear Technical Architecture defines product publication state, visibility, stock, media, and purchase checks. It does not define archived_at, restoration, or an archival transition matrix. However, local files now describe archival as approved behavior.

2. <span style="color:rgb(0, 176, 80)">Purchase behavior is not defined.  </span>
	The migration hides archived products from catalog queries. It does not enforce purchase eligibility because the order command does not exist yet. The architecture must define separate behavior for:
	- New purchases
	- Existing carts
	- Active reservations
	- Pending payments
	- Late-payment recovery
	- Existing orders and fulfillment
	- Assisted sales
	Archiving a product must stop new purchases, but it must not automatically break valid existing orders or payment recovery.

3. <span style="color:rgb(0, 176, 240)">Mutation while archived is undefined.  </span>
	Administrators can still change these values while the product is archived:
	- Status
	- Stock
	- Sales mode
	- Category
	- Product content
	- Media
	- Placements
	This can be valid, but the architecture must state whether an archived product is editable or frozen.

4. <span style="color:rgb(255, 0, 0)">Restoration can reactivate old merchandising automatically. </span> 
	Retained enabled placements become visible again after restoration if their time window is still valid. The product contract does not say whether this is intended.

5. <span style="color:rgb(112, 48, 160)">Public media URLs are a separate concern.  </span>
	Database RLS hides media rows, but it does not revoke a known public Storage URL or cached image. The architecture must define whether archive means catalog removal or media-access revocation.
