Repertorio commerce journey / database contract at 7b27013

Two customer paths. One order authority.

Account and guest customers can browse the same public catalog, but they reach checkout through different identity, cart, and later order-access controls. Both paths converge at one PostgreSQL command that recalculates commercial truth and creates the complete order in one transaction.

Database contract implemented Customer runtime planned Account actor: authenticated Guest actor: service_role at checkout Order command: public.create_order
CURRENT APP

The customer-facing root currently renders a starter page. The internal /~/architecture route is implemented. The repository has no storefront, Auth screens, checkout route, guest browser cart, payment adapter, webhook route, or customer order page. This map combines the implemented PostgreSQL contract with the explicit later runtime that must call it.

01 / route map

The complete journey at a glance

Colored lanes differ. Green nodes are shared database authority.

Shared entry

Open platform and browse the public catalog

Anonymous and authenticated sessions can discover active category paths and public products, media, and merchandising. Draft and archived products stay hidden. A visible zero-stock product still cannot enter a valid cart or order.

Identity and cart strategy split here
Account customer

Durable identity and cart

Supabase Auth identity becomes owner RLS authority.

A1
Sign up or sign in

Auth supplies auth.uid(). New users get one minimal profile and one welcome-email job atomically.

A2
Use profile and saved address

Owner-only data can help the interface, but checkout copies explicit contact and delivery inputs into immutable order snapshots.

A3
Build one database cart

The account has one persistent cart. Lines store only product and quantity; no line stores price or reserves stock.

A4
Request protected quote

The trusted server records quote evidence bound to the account cart and its current hash.

Guest customer

Local intent and narrow access

No account identity and no anonymous order-table access.

G1
Continue without signing in

The browser remains anonymous. Anonymous access is catalog discovery, not commerce-table authority.

G2
Build a browser-local cart

No guest cart row exists. Products, quantities, and destination remain untrusted browser intent.

G3
Ask the trusted server to validate

The server rechecks products, resolves packages, obtains the carrier quote, and calculates the canonical cart hash.

G4
Receive an opaque quote ID

The protected quote has cart_id = null and binds the guest cart hash, destination region, parcel data, service, amount, and expiry evidence.

Both paths now hold one protected quote
Authority convergence

public.create_order rechecks protected evidence and recalculates current commercial values

The account calls as authenticated. The trusted guest checkout calls as service_role with no Auth user. anon and guest_order cannot execute this command. The account path recalculates the live database-cart hash. The guest path matches the supplied hash to the protected quote hash. Both paths recheck current product eligibility, package inputs, prices, and stock.

Shared result

Placed order, payment attempt, stock reservation, and durable work

Both customer kinds enter the same order, payment, stock, recovery, cancellation, and fulfillment ledgers. Their later read sessions differ, but settlement authority does not.

02 / entry and identity

Access begins with different identity evidence

Neither path can author commercial truth.

Account identity

Auth user becomes the durable owner

Supabase Auth owns login email and authentication state. Repertorio creates one profile row for every new Auth user. The profile display fields and owner-managed Brazilian addresses are optional.

  • New Auth user, profile, and welcome job commit together.
  • RLS uses auth.uid() = user_id.
  • Profile and address data remain owner-only.
  • Auth deletion removes mutable account data but keeps order snapshots.
Guest identity

Anonymous browsing is not order identity

A guest does not get auth.uid(). The browser can see public catalog rows, but it cannot read orders, create commerce evidence, or call order lifecycle commands as anon.

  • No profile, address, or guest-cart row is required.
  • The trusted checkout route owns privileged calls.
  • Contact and delivery input become immutable order facts.
  • A separate post-order capability creates narrow read identity.
Shared catalog rule

Both visitors can request a product and quantity. PostgreSQL still rechecks publication, archive state, category path, sales mode, package data, price, and stock at the authoritative boundary.

browser = intent
03 / cart, shipping, coupon

Different cart storage, identical evidence standard

Only the trusted server can record quotes or preview coupon results.

Persistent account cart

Database-owned intent

get_or_create_cart, set_cart_item_quantity, and remove_cart_item derive the owner. A line stores product plus positive quantity only.

  • One non-expiring cart for each account.
  • New writes require a current public direct-stock product.
  • Stale lines remain visible and removable.
  • Quote evidence binds the cart ID and recalculated cart hash.
Browser-local guest cart

Untrusted local intent

Product IDs and quantities stay in browser state. The trusted server validates them before it records a quote with no cart ID.

  • No anonymous cart-table grant exists.
  • Canonical sorted product and quantity pairs form the cart hash.
  • Resolved package and parcel data become protected evidence.
  • The browser receives only the opaque quote UUID.
Quote and coupon authority

The quote binds the destination region: country, postal code, and state. It also binds carrier service, amount, provider reference, package and parcel hashes, and a maximum 24-hour expiry. Coupon preview returns only a safe calculated result. It does not consume the global campaign limit.

service_role only
04 / atomic order transaction

One command converts intent into retained truth

Any failed step rolls back every earlier effect.

01 Derive caller and validate inputs

Derive account or trusted guest authority. Validate the required quote UUID, 32-byte cart hash, and global idempotency key. Other accepted fields are constrained when their rows are inserted.

02 Serialize and check replay

Take the domain advisory lock before the first existing-order lookup. An exact retry stays pinned to payment attempt sequence 1.

03 Load quote and verify the path

Load the protected quote. Lock and verify the account-owned cart, or require guest quote evidence with no cart ID. The guest hash comparison occurs when checkout evidence is consumed.

04 Lock products by UUID

Recalculate package inputs, catalog eligibility, current prices, subtotal, and available stock.

05 Consume checkout evidence

Lock and consume the unused, unexpired quote and optional coupon. Validate destination region and package evidence, then calculate the discount and final total.

06 Freeze order snapshots

Insert the placed order and item rows with contact, delivery, product, package, media, price, shipping, coupon, and total facts.

07 Create payment attempt and work

Create attempt sequence 1, record its two transitions, enqueue payment-session-create, and set the current payment pointer.

08 Reserve every stock line

Decrement available stock and create every direct-stock reservation. All lines succeed or none do.

09 Record placement and confirmation

Record the order placed transition and enqueue the order-confirmation-email job.

10 Issue guest capability and return

For a guest, generate the one-order capability and store only its hash. Return the account or guest result after every effect is ready to commit.

Return contract

Both paths receive order_id and payment_attempt_id. Only the first successful guest call receives guest_access_token. An exact retry must keep the original quote ID, supplied cart hash, customer, contact, delivery, coupon, payment, and provider inputs. The replay path does not re-read the live cart, so a later cart mutation does not by itself cause a conflict. An exact guest retry never returns the raw token again.

05 / after order creation

The read paths separate again

Both receive narrow, RLS-filtered table reads, never provider or recovery secrets.

Account order access

Owner RLS follows the Auth session

1

Browser sends the authenticated Supabase session.

2

PostgreSQL evaluates auth.uid() = orders.user_id.

3

The owner reads granted order and item columns plus payment-attempt ID, order ID, sequence, amount, currency, state, provider expiry, and timestamps.

4

Provider IDs, raw status, recovery proof, and operational evidence stay hidden.

Guest order access

One secret becomes one restricted session

1

Database generates at least 256 random bits and stores only SHA-256. Checkout access expires after seven days.

2

Trusted server keeps a separate random exchange key in a secure same-site HttpOnly cookie.

3

exchange_guest_order_access stores only the exchange-key hash and returns access ID, order ID, and maximum expiry.

4

Later server route mints a restricted JWT: role guest_order, sub = access_id, fixed session-kind claim.

5

RLS rechecks exchange, expiry, revocation, and replacement on every one-order read.

Guest replay and revocation rule

While the capability remains unexpired and unrevoked, the same capability and exchange key return the first result. A different key is denied as replay. An expired, revoked, or replaced capability fails before replay return. Replacement atomically creates one unexchanged successor, so an old JWT loses access on its next database read.

read-only / one order
06 / shared payment path

Customer kind no longer changes settlement rules

Provider redirects never create database payment truth.

1 / durable intent payment-session-create

The order transaction creates one payment-session-create job and one order-confirmation-email job. Each has a stable business key.

2 / provider session Attempt becomes pending

A later worker stores safe session identity and aligns reservation expiry.

3 / verified intake Record webhook subject

One provider event binds to one exact attempt and provider reference.

4 / normalized fact Store payment evidence

Provider, checkout, payment, amount, currency, state, source, and sequence become append-only truth.

5 / classification Select one candidate

Paid evidence is ordered by recorded sequence and then attempt ID. Immediate settlement also requires no existing settlement, a non-cancelled order, no other active payable attempt, safe stock coverage, and no open blocking recovery gate.

6 / forward gate Recheck every forward gate

Before handoff, forward fulfillment requires a same-order settlement pointer to a currently paid attempt, no active paid- cancellation intent, and no open blocking payment-recovery gate. After authoritative handoff, verified carrier delivery can continue from handoff evidence even after a refund.

Current runtime gap

AbacatePay session creation, webhook verification, reconciliation, outbox execution, and customer payment pages are not implemented. PostgreSQL already defines the exact commands and failure behavior that those later adapters must use.

07 / authority comparison

What each customer path can and cannot do

The customer session never becomes a lifecycle worker.

Boundary Account customer Guest customer Database authority
Catalog Public catalog reads with authenticated session. Public catalog reads as anonymous visitor. RLS exposes only active public catalog rows.
Identity Supabase Auth user, profile, and optional saved addresses. No account. Later capability gives one-order read identity. Auth owns login; capability table owns guest scope.
Cart One persistent owner cart in PostgreSQL. Browser-local intent; no guest cart row. Cart or quote evidence is rechecked at checkout.
Quote Bound to cart ID and cart hash. Bound to guest cart hash with cart_id = null. Only trusted server records immutable one-use evidence.
Create order authenticated executes create_order. Trusted service_role executes on guest behalf. anon and guest_order cannot execute it.
Order reads Owner RLS through auth.uid(). Restricted JWT through exchanged access-row identity. Both read only safe order, item, and payment columns.
Order mutation No direct issued-order mutation. No direct mutation or lifecycle commands. Guarded staff and worker commands own later transitions.
Payment authority Cannot mark payment paid or select settlement. Cannot mark payment paid or select settlement. Verified provider facts and settlement guards decide.
A customer can request an action. Only the protected command can accept it as business truth.

Implemented and tested

  • Auth profile and address ownership.
  • Account cart commands and guest quote evidence.
