1 — Core idea
Identity
Who am I?

The app uses APP_ENVIRONMENT, not NODE_ENV, to identify local, Preview, staging, or production.

Evidence
Can I prove it?

The branch, Vercel level, GitHub repository, Supabase project, and secret scope must match the checked-in policy.

Result
Allow or stop

A valid deployment starts. A missing or contradictory value stops the build or first server evaluation.

2 — The problem it solves

Before: one Vercel label, two trust levels

On Vercel Hobby, both dev and feature branches report VERCEL_ENV=preview.

  • The app could not reliably separate staging from a feature Preview.
  • Both environments use the shared staging Supabase project.
  • A wrongly scoped secret could give a feature branch administrative access.
  • A wrong workflow could promote migrations from an unsafe context.
  • Different branches could mix their test records.

After: application identity plus proof

The application adds its own identity and checks it against platform facts.

  • preview means a feature branch with no privileged key.
  • staging means exactly dev on Vercel Preview.
  • production means exactly main on Vercel Production.
  • Each Preview gets a stable test-data namespace.
  • Migration promotion requires a separate protected GitHub context.
Why not NODE_ENV? Next.js uses NODE_ENV=production for optimized Vercel Preview builds. It describes the framework build mode, not the business deployment environment.

Parse shape

04
Compare policy
Branch, repository, Vercel level, Supabase target, and secret rules must agree.
05
Allow or fail
Return safe server values or throw an error before application use.
If validation passes

The app receives derived capabilities

  • environment
  • hasPrivilegedSupabaseAccess
  • previewIsolationId
If validation fails

The app does not continue silently

Wrong repository, wrong branch, wrong Supabase target, forbidden secret, missing identity, and unsupported production all cause a hard failure.

Defense in depth: Feature Previews do not receive SUPABASE_SECRET_KEY. In addition, createAdminSupabaseClient() checks hasPrivilegedSupabaseAccess and refuses to create an admin client.

7 — Try the decision model
DENIED

Feature Preview receives admin secret

Feature Previews must not receive SUPABASE_SECRET_KEY. The deployment fails instead of accepting excessive privilege.

  • Identity: preview
  • Branch: feature branch
  • Secret: present, but forbidden

9 — Scope and safety boundaries
This PR does
  • Defines deployment identity.
  • Checks platform and database evidence.
  • Removes admin privilege from feature Previews.
  • Creates stable test namespaces.
  • Creates a migration context guard.
  • Documents and tests the contract.
This PR does not
  • Create or run a database migration.
  • Create the promotion workflow.
  • Configure production values.
  • Create the production Supabase project.
  • Give a Preview administrative access.
  • Replace RLS or application authorization.
The final mental model: environment variables are claims. Branch, platform, repository, project, and secret scope are evidence. The application grants a capability only when every fact agrees with policy.
