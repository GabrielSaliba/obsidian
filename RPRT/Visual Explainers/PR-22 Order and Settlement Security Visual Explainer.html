TL;DR

PostgreSQL now owns every commercial decision that can change money, stock, or delivery authority. Verified provider payment is stored as permanent evidence, but it cannot authorize fulfillment by itself. Only one same-order settlement pointer can grant that authority, and only after payment, stock, cancellation, and recovery guards pass under a stable lock order. Unsafe outcomes stay visible and move to explicit recovery instead of being overwritten.

02

How authority moves through the system

Callers do not write commercial tables directly. They call narrow security-definer commands. Those commands derive the actor, lock the required rows, validate current evidence, commit business truth, and create durable work in one transaction.

The database command boundary turns verified input into one local outcome and one durable evidence trail.
03

The 13 new evidence tables

Six schema migrations create 11 public domain tables. The payment command migration adds one public webhook-subject table and one private normalized-fact table.

Domain Table What it stores Main safety rule
Order orders Identity, customer and delivery snapshots, totals, lifecycle, and payment pointers. Issued commercial facts cannot be rewritten or deleted.
Order order_items Product, sales mode, quantity, package, price, and line-total snapshots. Same-order product facts freeze after the order leaves draft.
Guest guest_order_access Capability hash, exchange-key hash, expiry, revocation, and replacement lineage. Raw capability is never stored; access stays bound to one order.
Payment payment_attempts Each provider checkout attempt, amount, currency, state, and provider identity. Every retry keeps a separate identity; only one attempt can be actively payable.
Payment webhook_event_subjects Immutable event-to-attempt or event-to-order subject binding. One provider event cannot be reused for another local subject.
Payment private.payment_evidence_facts Normalized provider state, status, IDs, amount, currency, and source, plus a lock-serialized recorded sequence. An exact retry must match every normalized field. The recorded sequence selects paid precedence.
Stock stock_reservations Direct-stock reservation identity, quantity, attempts, expiry, and state. Only active to consumed or active to released is valid.
Recovery payment_recovery_cases Late, duplicate, or cancelled-order paid facts. Blocking behavior is fixed by recovery kind and exact paid transition.
Recovery payment_recovery_resolutions One accepted settlement, verified refund, or administrative closure. One immutable resolution per case, bound to exact transition evidence.
Cancellation order_cancellation_intents Refund-first paid cancellation request and staff evidence. One permanent intent per order; it cannot be withdrawn.
Cancellation paid_cancellation_stock_restorations One stock restoration fact for each consumed reservation. The row and quantity prove that stock was restored only once.
Handoff recovery post_handoff_refund_cases Verified refund after carrier, pickup, or local handoff. Payment can change while delivery and consumed-stock history stay unchanged.
Handoff recovery post_handoff_refund_resolutions Administrative evidence that closes one post-handoff case. Resolution cannot rewrite payment, fulfillment, settlement, or stock truth.
All 12 new public tables enable RLS and deny broad direct mutation. private.payment_evidence_facts is the thirteenth table; it has no application-role table grants and rejects update and delete.
04

Four lifecycles stay separate

Order

Commercial lifecycle

The order records commercial existence. It does not copy payment or delivery state.

draft→placed
placed→cancelled
placed→completed
Payment

Provider fact lifecycle

Attempts preserve retries and ambiguous provider results without changing order state.

not_started→creating→pending
creation_unknown→paid / failed
paid→refund_pending→refunded
Stock

Reservation lifecycle

Available stock changes once for reserve, release, or approved restoration.

active→consumed
active→released
Fulfillment

Physical delivery lifecycle

Every forward edge needs current settlement authority and clear recovery gates.

unfulfilled→in_production
ready→in_transit
exception→fulfilled
Core distinction

current_payment_attempt_id selects retry work. It is not fulfillment authority. Only settlement_payment_attempt_id can grant forward authority, and it must point to a same-order verified paid attempt that passes every gate.

Terminal states agree in both directions

orders.state = 'cancelled' if and only if fulfillment is cancelled. orders.state = 'completed' if and only if fulfillment is fulfilled. A placed order cannot carry either terminal fulfillment state.

Order creation paths

public.create_order

Account checkout or trusted guest checkout becomes one placed order.

Administrator-negotiated work stays non-payable until explicit issue.

1

2

Replay and snapshot hardening

Exact storefront and assisted-issue replays stay pinned to payment attempt sequence 1. Changed cart hash, order input, issue key, or payment input fails with 23514, and a replay never returns a second raw guest token. Draft assisted lines remain editable; after issue, direct line insert, update, move, and delete all fail. Order deletion and owner reassignment also fail, while Auth user deletion follows the declared foreign key and sets orders.user_id to null.

06

Guest access without anonymous order reads

Issue

Generate 256-bit capability

The service gets the raw capability once. PostgreSQL stores only SHA-256 and a finite expiry.

Exchange

Bind a second secret

The first exchange stores only the secure-cookie exchange-key hash. A different key is replay and fails.

Read

Derive one-order scope

RLS reads the access ID from the restricted JWT and rechecks order, exchange, expiry, and revocation. 

// The later server route must mint this restricted session.
role = "guest_order"
sub = guest_order_access.id
rprt_session_kind = "guest_order"
exp <= guest_order_access.expires_at

// RLS never trusts a caller-supplied order ID.
order_scope = guest_order_access.order_id
Fail-closed database role

guest_order is NOLOGIN, NOINHERIT, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOREPLICATION, and NOBYPASSRLS. Migration rejects every unsafe flag or unexpected membership. Only authenticator can assume the role, without admin or inherited membership. A creator administration grant may remain only when it cannot inherit or set the role. Malformed and expired capabilities fail, and an exchanged guest still has only the two order-ledger SELECT policies.

07

From provider payment to settlement authority

record_commerce_webhook_event first binds one provider event to one exact local subject. private.apply_payment_fact then stores normalized evidence and classifies the result under the order lock.

Order already cancelled?
→
cancelled_order_refundKeep the order terminal, move the attempt to refund work, and open a non-blocking case.
Settlement exists or another paid fact wins?
→
duplicate_refundPreserve both verified paid facts, keep the first settlement, and request one full refund.
Payable competitor, missing stock, or blocking gate?
→
settlement_recoveryDo not grant authority. Create blocking recovery evidence and durable operations work.
All local guards pass?
→
Accept settlementConsume active reservations, set the same-order settlement pointer, and enqueue one approval email.
Deterministic winner

Recorded sequence, then attempt ID

The database assigns a unique evidence sequence only after it holds the order and related locks. The lowest sequence wins; payment-attempt UUID is the tie-breaker. Statement time, transition time, and transition UUID do not select authority. A fully refunded earlier attempt does not block a later valid settlement.

Late paid recovery

Reacquire all stock or refund

Recovery can supersede only untouched no-call attempts. It reacquires every direct-stock line or changes to full-refund work with no partial stock effect.

08

Cancellation, refunds, and handoff

Unpaid cancellation

Cancel only when payment is safe

Untouched attempts can fail with no-call evidence. Creating, unknown, pending, paid, and refund states block cancellation. Active reservations release and stock increments once.

Paid before handoff

Refund first, then cancel

The intent blocks fulfillment and creates full-refund work. Verified refund cancels order and fulfillment and writes one restoration fact per consumed reservation.

Refund after handoff

Preserve physical truth

The attempt can become refunded, but order, fulfillment, settlement, and consumed stock remain. A separate case and immediate alert own recovery.

Shipping-label guard

Paid cancellation can suppress only a pristine, unclaimed label job with zero provider calls, no fingerprint, no dispatch time, and no call evidence. Processing, completed, or dead-letter state rejects cancellation independently. A fingerprint, dispatch time, nonzero call count, or provider-call row also rejects it independently.

Exact recovery evidence

One event, one attempt, one outcome

A recovery case must bind the order and attempt to the exact normalized paid webhook: provider, subject, reference, actor, source, transition, canonical reason, event operation reference, checkout, payment, amount, currency, and state must agree. Settlement recovery is valid only while that attempt remains paid. Verified-refund and administrative resolutions require their own exact evidence and cannot substitute for each other.

Exact restoration and handoff evidence

Physical truth stays bound

Stock restoration binds the consumed reservation and quantity to the accepted settlement, normalized refund, webhook subject, cancellation transition, and intent. Post-handoff recovery binds the current locked fulfillment snapshot, retained settlement, normalized refund, and an administrator-authorized handoff. Its closure must use the same authorized administrator, reason, and proof.

Roles, RLS, and direct-access denial

Function hardening

Reviewed public commands use security definer, set search_path = '', revoke default execution, and grant only the exact roles that own each command path.

Stored administrator authorization

Every domain transition stores a non-null authorization fact. A before-insert security-definer trigger requires an administrator actor to equal auth.uid() and to have current admin_users membership. It records true only after that check; non-administrator transitions record false. Migration backfill fails if existing administrator evidence cannot be proved, and later staff removal does not invalidate stored authorization. Payment-recovery administrative replay must keep the same actor, reason, proof, and idempotency key. Post-handoff closure keeps the same actor, reason, and proof and has no separate idempotency-key parameter.
