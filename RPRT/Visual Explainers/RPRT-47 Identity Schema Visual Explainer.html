01

Why this boundary exists

Before

Auth had no customer data boundary

  • No profile row for a new Auth principal.
  • No saved-address ownership model.
  • Welcome delivery existed as an outbox type, but no signup producer used it.
  • Guest and account identity responsibilities were mixed in one issue.
After

Each authority has one clear home

  • Login email: auth.users.
  • Display data: owner-only profiles.
  • Saved delivery data: owner-only addresses.
  • Staff authority: protected admin_users.
  • Guest order access: transferred to RPRT-46 with orders.
02

Concepts used by this PR

Supabase Auth

The trusted login system. Its auth.users.id value is the identity used by all new customer rows.

Foreign key

A database link that requires an address or profile owner to exist in auth.users.

SQL grant

The first access gate. It controls which role can use an operation and which columns it can write.

Row-level security

The second access gate. RLS checks each row, so one customer cannot read or change another customer's data.

Trigger and transaction

A trigger runs after an Auth insert. All trigger writes commit or roll back with that insert.

Outbox and idempotency

The outbox stores durable email work. A stable business key makes an exact retry return the same job.

using selects rows that the caller can update. with check also checks the new row. Column grants stop changes to ownership and timestamps even when the row belongs to the caller.

05

One signup, one atomic outcome

1Auth inserts user

The trusted UUID and Auth creation time enter PostgreSQL.

2Trigger derives identity

No caller user ID and no user metadata are trusted.

3Profile initializes

One minimal row, protected by the Auth UUID primary key.

4Welcome job enqueues

Stable key: profile ID plus normalized creation time.

5Audit commits

One pending transition. Any conflict rolls back every new row.

No partial accounts

If the profile constraint or outbox evidence fails, the Auth insert fails. The test suite proves that no Auth user or profile remains after a conflicting welcome key.

supabase/migrations/20260819205344_add_identity_access_schema.sql:176-219 
create function private.handle_new_auth_user()
returns trigger language plpgsql
security definer set search_path = ''
as $$
begin
  insert into public.profiles (user_id, created_at, updated_at)
  values (new.id, profile_created_at, profile_created_at)
  on conflict (user_id) do nothing;

  perform public.enqueue_outbox_job(
    'welcome-customer-email',
    'welcome-customer-email:' || new.id::text || ':' || normalized_profile_created_at,
    pg_catalog.jsonb_build_object('profile_id', new.id::text, ...), 1
  );
  return new;
end;
$$;

security definer gives the protected function enough rights to create rows. The empty search_path requires qualified object names and prevents name substitution. The function uses only trusted fields from the inserted Auth row.

Check your understanding

Why are both grants and RLS necessary?

Grants control operations and columns. RLS controls rows. Together, they stop a user from changing protected fields and from accessing another user's rows.

Why is user_id the profile primary key?

It enforces one profile at most for each Auth user without a second identity value.

Why does the trigger use SECURITY DEFINER?

Application roles cannot insert profiles or outbox jobs. The protected trigger must use its owner's rights to do this work.

What makes signup atomic?

The trigger runs inside the Auth insert transaction. An exception in profile or outbox work rolls back all writes, including the Auth user.

Why include creation time in the welcome business key?

It identifies one stable account-creation event. Repeating the same evidence returns the same job, while different evidence is rejected.

Why does administrator membership not widen access?

The profile and address policies check only auth.uid() = user_id. They do not query admin_users.
