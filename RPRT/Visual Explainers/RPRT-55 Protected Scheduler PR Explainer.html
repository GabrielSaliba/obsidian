TL;DR

This stack does not schedule a production job. It creates the protected factory that every later job must use. Authentication happens before observability context or handler work, handlers receive strict batch and time limits, duplicate safety is their durable responsibility, and every authorized invocation produces one bounded response and one final wide event.

02

Why this boundary exists

Before

  • No shared scheduler authentication contract.
  • No common batch or whole-route deadline.
  • Later jobs could invent different retry rules.
  • No approved final-event fields for scheduled work.
  • Duplicate-delivery expectations existed only in issue text.

After

  • One exact bearer gate through server-only CRON_SECRET.
  • One handler interface with limit, deadline, signal, and correlation.
  • One outcome vocabulary for success, duplicate, failure, and retry.
  • One final safe wide event for each authorized operation.
  • Tests prove bounds and duplicate-safe fixture behavior.
03

The authorized execution path

Request GET invocation

Cookies and browser sessions have no authority.

Trust gate Exact bearer check

Reject before context creation, loading, or execution.

Observe Create operation

Generate request and operation IDs through RPRT-5.

Bound Load up to limit

Pass batch limit, deadline, and shared abort signal.

Execute Process each item

Require a stable business key; stop before new work at deadline.

Finalize Response + event

Return bounded counts and emit one final safe wide event.

Unauthorized branch: returns HTTP 401 with no-store. The observer, loader, and executor are not called.

Outcome semantics

ConditionHTTPOperation resultReviewer meaning
All loaded work succeeds or is already applied 200 success No retry remains.
One or more items have a final classified failure 200 partial_failure The handler owns durable final evidence; repeating the batch is unsafe or unnecessary.
Retry-safe work or loaded work remains 503 retry The next controlled invocation can continue durable work. Vercel Cron does not retry automatically.
Timer expiry or unexpected exception 500 error Abort the signal and do not assume an in-flight external effect is safe to repeat.
05

Security and privacy boundary

Credential

Server only

CRON_SECRET must have at least 16 characters, cannot use a public prefix, and is forbidden from feature Preview configuration.

Idempotency

Handler owned

The runner passes a stable business key. Durable database or provider guards must make duplicate delivery safe across requests and runtime instances.

Telemetry

Counts, not payloads

Events include job type, limits, counts, deadline state, status, and correlation. They exclude secrets, items, business keys, cookies, and raw messages.

07

Where the reviewer should focus

01

Authentication order

Confirm the exact bearer check happens before observer.observe, load, and execute. This prevents unauthorized work and unauthorized correlation events.

02

Duplicate contract

Confirm the runner does not claim that process memory is durable. The production handler must use a database command, lock, lease, or provider-supported idempotency key.

03

Deadline and ambiguity

Confirm timer expiry aborts the signal and returns an error instead of converting an unsettled external effect into a blind retry.

04

Partial failure versus retry

Confirm a final classified item failure returns HTTP 200, while retry-safe or unprocessed work returns 503 and remains durable for a future run.

05

Outbound privacy

Confirm the response and final event contain bounded counts and correlation only. The secret, work item, business key, cookie, and raw exception message must stay absent.

Explicitly out of scope

This stack provides a framework, not a deployed schedule. It does not add a fixture route, vercel.json cron entry, outbox claimant, payment reconciliation handler, shipment tracker, cleanup command, provider call, production secret, or live scheduler proof. Those belong to their delivery milestones and must use the reviewed factory.
