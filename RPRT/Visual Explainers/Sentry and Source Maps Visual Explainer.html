RPRT-60 learning brief

Sentry makes production errors readable and actionable.

Sentry receives unexpected exceptions, groups similar failures into issues, connects them to a release, restores readable source locations, and notifies the operators who can respond.

01

The basic Sentry mental model

Runtime flow: exception capture is separate from business audit and normal operational logging.
Capture

Unexpected exceptions

The SDK captures an error, a safe stack trace, release identity, environment, and approved correlation fields.

Group

Many events become one issue

Similar failures are grouped so operators can see frequency, affected releases, and regressions instead of isolated logs.

Respond

Operators receive useful alerts

Alert rules notify the approved inbox for new or escalating staging exceptions without sending normal success events.

02

DSN and source-map token do different jobs

Event route

DSN

The SDK uses the Data Source Name to send exception events to the correct Sentry project.

  • Used while the application runs.
  • Identifies the Sentry project and ingest endpoint.
  • Can exist in client configuration.
  • Cannot manage the organization or upload source maps.
Upload authority

Source-map auth token

A trusted build or release process uses this secret to upload source maps and release metadata.

  • Used only during a build or release step.
  • Must stay in a trusted secret store.
  • Must never enter browser code or repository files.
  • Can be revoked without changing event ingestion.
GitHub path

repertorio-github-source-maps

A future Sentry organization token for a trusted CI upload job. Create it only when RPRT-5 provides that job.

Vercel path

repertorio-vercel-source-maps

A separate future token if Vercel performs uploads. Separate tokens let one path be revoked without stopping the other.

Initial setup rule: create the Sentry project and record the approved token names and storage locations. Do not create upload tokens until RPRT-5 implements and verifies the upload path.
03

How source maps restore the original code

Source maps are build artifacts. The token uploads them; the DSN sends runtime events.
Without maps

app-a91f.js:1:29442

The exception points to generated, compressed JavaScript. The location is difficult to connect to the source change.

With maps

src/app/checkout.ts:184

Sentry shows the original file, function, line, and nearby code for the exact release that produced the error.

Safety boundary

Before an event leaves the app

  • Remove cookies, authorization headers, and request bodies.
  • Remove names, email, phone, CPF, addresses, and payment data.
  • Allow only approved correlation and deployment fields.
  • Do not change a business result if Sentry fails.
  • Do not send normal informational events to Sentry.
Important: a real setup also needs server and edge initialization, safe error serialization, tests with fake values, a release identity, token isolation, and proof that uploaded source maps do not remain in public browser output.
05

The selected initial rollout

Local OFF

Use local logs and test doubles. Do not consume Sentry quota.

Feature Preview OFF

PR branches do not send test exceptions or receive upload tokens.

Staging ON: dev branch

First environment for exception, alert, release, and source-map proof.

Production OFF

Enable only after the production environment is approved.
